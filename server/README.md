# herewego-server

가보자고 Pleos 앱의 백엔드입니다. Kotlin + Ktor.

안드로이드 앱과 별도의 Gradle 빌드이므로 이 디렉터리에서 빌드하고 실행합니다.

## API

| 엔드포인트                                                | 기능                                          |
|-----------------------------------------------------------|-----------------------------------------------|
| `GET /healthz`                                            | 헬스 체크                                     |
| `POST /v1/explore`                                        | 기능 1: 현재 위치에서 갈 만한 곳              |
| `GET /v1/purposes`, `POST /v1/purpose/plan`               | 기능 2: 목적(프리셋, 자유 입력)에 맞는 경유지 |
| `POST /v1/gap/plan`                                       | 기능 3: 두 일정 사이 빈 시간에 갈 곳          |
| `GET /v1/places/search`                                   | 장소 검색                                     |
| `GET/PUT /v1/profile`, `POST /v1/profile/visits`          | 기기별 관심사·방문 횟수                       |
| `GET/POST /v1/schedules`, `PUT/DELETE /v1/schedules/{id}` | 기기별 일정                                   |

`/v1` 요청에는 `X-Device-Id`가 필요하고, `APP_KEY`가 설정되어 있으면 `X-App-Key`도 필요합니다.

## 추천 방식

1. Google Places API (New)에서 평점, 요일별 영업시간, 리뷰 발췌와 함께 후보를 가져옵니다.
2. 엔진이 불가능한 후보(오늘 휴무, 영업시간 밖, 너무 먼 곳)를 제외한 후 거리, 우회, 시간을 직선거리로 추정합니다. 실제 주행 시간은 차량에서 계산하여 보정하고, 서버에서는 경로 탐색을 수행하지 않습니다.
3. LLM이 후보의 사실과 평점·영업시간·리뷰를 보고 최종 장소와 순서를 고르고 이유를 추천합니다.
4. 3단계와 동시에, 추천될 만한 후보들의 리뷰를 LLM 호출 한 번으로 읽어 대표 메뉴(또는 즐길 거리)와 리뷰 요약을 생성합니다.

`"rank": "rules"`를 보내면 3단계를 건너뛰고 4단계는 시작만 해 둡니다. 앱은 먼저 이걸로 빠르게(1초 미만) 받고, 다시 Gemini 순위를 요청합니다. LLM API 요청이 실패하거나 `LLM_TIMEOUT_MS`를 넘기면 규칙 기반 결과를 `"rankedBy": "rules"`로 반환합니다. 평점과 영업시간은 어느 쪽이든 첫 응답부터 들어 있고, 대표 메뉴와 리뷰 요약은 요약이 끝난 뒤(6시간 캐시)부터 들어갑니다.

### 검색 호출 수

Places 검색은 호출마다 요금이 붙고(평점·영업시간·리뷰 포함 호출 1,000건당 $40, 월 1,000건 무료) 호출당 결과는 20건입니다. 그래서 카테고리마다 따로 찾지 않습니다.

| 기능      | 찾는 방법                                                                                       | 호출 수                      |
|-----------|-------------------------------------------------------------------------------------------------|------------------------------|
| 지금 여기 | 반경 2km 주변 검색, 카테고리를 네 묶음(식당 / 카페·베이커리 / 공원·전시·서점·소품 / 헬스장)으로 | 4 (+ 도착한 장소 확인 1)     |
| 가는 길에 | 출발지→목적지 직선을 최대 3구간(구간당 8km)으로 나눈 사각형 안에서 필요 품목마다 글자 검색      | 품목 수 × 구간 수 (보통 4~8) |
| 빈 시간   | A 주변, B 주변, 둘이 멀면 그 사이를 세 묶음(헬스장 제외)으로 주변 검색                          | 3~9                          |
| 장소 검색 | 글자 검색, 이름·위치만 (더 싼 요금)                                                             | 1                            |

같은 자리(약 100m 격자)의 검색 결과는 10분 동안 메모리에 캐시합니다. Google의 '경로를 따라 검색' 옵션은 직선을 넣으면 경로에서 10km 넘게 벗어난 곳을 돌려줘서 쓰지 않습니다.

### 알아 둘 점

- 장소에는 출처 링크 `mapsUrl`이 함께 오며, 앱은 평점·영업시간·메뉴·리뷰를 보여 줄 때 Google Maps 출처를 표시해야 합니다.
- `stayMinutes`는 Google이 주지 않아 장소 종류별 기본값입니다 (패스트푸드 25분, 고깃집 80분 등).
- 상호에 붙은 검색 노출용 문구("… | Gangnam BBQ", 한글 이름 뒤의 영문 표기)는 떼어 냅니다.
- 영업시간이 등록되지 않은 곳(공원 등)은 카테고리 기본값을 쓰고 `hoursEstimated: true`로 표시합니다.

`GOOGLE_PLACES_KEY`가 없으면 장소 관련 엔드포인트는 503을 반환합니다. `GEMINI_API_KEY`가 없으면 자유 입력 목적을 제외하고 규칙 기반으로 동작하며, 평점과 영업시간은 그대로 나오고 대표 메뉴와 리뷰 요약만 빠집니다.

## 실행

```sh
cp .env.example .env      # 키 입력
./gradlew run             # .env가 아니라 환경 변수를 읽음
./gradlew test
```

Docker 또는 Podman:

```sh
docker compose up --build
```

## 과금 보호 / 요청 제한

기본값으로 켜져 있습니다. 별도의 Redis나 프록시 설정 없이 모든 `/v1` 경로에 적용합니다.

| 환경 변수 | 기본값 | 범위 |
| --- | ---: | --- |
| `API_REQUESTS_PER_MINUTE` | 60 | 서버 전체 `/v1` 요청/분 |
| `DEVICE_REQUESTS_PER_MINUTE` | 20 | 기기별 `/v1` 요청/분 |
| `PLACES_CALLS_PER_MINUTE` | 40 | 실제 Places 호출/UTC 분 |
| `PLACES_CALLS_PER_DAY` | 100 | 실제 Places 호출/UTC 일 |
| `PLACES_CALLS_PER_MONTH` | 1000 | 실제 Places 호출/UTC 월 |
| `GEMINI_CALLS_PER_MINUTE` | 10 | 실제 Gemini 호출/UTC 분 |
| `GEMINI_CALLS_PER_DAY` | 60 | 실제 Gemini 호출/UTC 일 |
| `GEMINI_CALLS_PER_MONTH` | 500 | 실제 Gemini 호출/UTC 월 |

- 요청 제한은 고정 1분 창이며, 초과 시 JSON 오류와 **HTTP 429 + `Retry-After`(초)** 를 반환합니다. `/healthz`는 제외합니다. 기기 ID를 바꿔도 서버 전체 한도 및 외부 호출 한도는 우회하지 못합니다. `X-Forwarded-For` 등 클라이언트가 조작할 수 있는 IP 헤더를 신뢰하지 않습니다.
- **실제 외부 API 시도마다**, 전송 전에 `DB_PATH`의 SQLite `usage_quota`에 분·일·월 사용량을 원자적으로 예약합니다. 캐시 적중은 차감하지 않지만, 이름 검색, AI 순위, 자유 입력 목적 분석, 백그라운드 리뷰 요약은 모두 포함합니다. 실패·취소도 환불하지 않아 재시도로 한도를 우회하지 못합니다. 동시 요청도 한도를 초과할 수 없고 DB 오류 시 외부 요청을 보내지 않습니다.
- **0은 무제한이 아니라 차단입니다.** 예를 들어 `PLACES_CALLS_PER_DAY=0`, `GEMINI_CALLS_PER_DAY=0`이면 해당 유료 API를 즉시 막습니다. 음수·잘못된 숫자는 시작 시 오류를 냅니다.
- 한도 소진 시 Places 요청은 429를 반환하고, Gemini 순위·요약은 기존 오류 처리에 따라 규칙 기반/요약 없는 결과로 대체될 수 있습니다. `rank=rules`만으로는 리뷰 요약 비용을 끄지 못합니다.
- 외부 동시 호출은 Places 4개, Gemini 2개로 제한합니다. 정상 경로 계획의 병렬 검색은 대기열에서 처리합니다. Gemini 입력(시스템·사용자·스키마 합)은 64,000자 이하, 출력은 4,096토큰 이하로 제한합니다. 검색어는 256자 이하입니다.
- **운영 DB를 유지하세요.** 재시작해도 유료 호출 한도는 유지되지만 DB 삭제/교체, `:memory:`, 복제본마다 별도 DB를 쓰면 예산도 따로 생깁니다. 기존 과거 호출은 소급 집계하지 않습니다. 다중 인스턴스 운영 시 공유된 중앙 한도 저장소 또는 게이트웨이가 필요합니다.
- 이것은 **호출 수 제한이지 금액 보증이 아닙니다.** 요금제·모델·토큰 수에 따라 비용이 달라집니다. 배포 시 Google Cloud의 Places API 쿼터와 Gemini 프로젝트 쿼터도 낮추고, 예산 알림을 설정하세요. **예산 알림 자체는 과금을 자동 중단하지 않습니다.** API 키의 API/IP 제한도 설정하세요. 다른 서비스가 같은 키를 쓰는 비용은 이 서버가 막지 못합니다.

## 설정

| 변수                 | 설명                                                  |
|----------------------|-------------------------------------------------------|
| `PORT`               | 포트, 기본 8080                                       |
| `APP_KEY`            | 앱이 `X-App-Key`로 보내는 공유 키. 없으면 검사 안 함  |
| `GOOGLE_PLACES_KEY`  | Places API (New)를 켠 Google Maps Platform 키         |
| `GEMINI_API_KEY`     | Google AI Studio 키                                   |
| `LLM_MODEL`          | 기본 `gemini-4-hydrogen`                              |
| `LLM_TIMEOUT_MS`     | 순위 LLM 최대 대기 시간, 기본 15000                   |
| `INSIGHT_TIMEOUT_MS` | 리뷰 요약 대기 시간(순위와 동시에 돎), 기본 10000     |
| `INSIGHT_MAX_PLACES` | 요청당 새로 요약할 장소 수, 기본 24. 0이면 요약 안 함 |
| `DB_PATH`            | SQLite 파일, 기본 `data/herewego.db`                  |
